# HHMusic — Agent Guide

## Quick Start

```bash
npm install                       # install deps + auto-updates yt-dlp binary (postinstall)
# edit .env (copy .env.example)
npm start                         # node index.js (<1000 servers)
node shard.js                     # ShardingManager (>1000 servers)
npm test                          # node --check index.js (syntax check only — no test framework)
```

## Non-Obvious Facts

- **Startup sequence** (`index.js`): `commandLoader.js` is `require`d at top level (index.js:115) for its side effect — registers slash commands via the Discord REST API. Client creation is wrapped in `setTimeout(..., 5000)` (index.js:640) to let command registration finish before connecting. When switching from `GUILD_ID` (test) to global deployment, run `node scripts/cleanup-guild-commands.js` (pass a guild ID or use `GUILD_ID` env) to wipe lingering guild-scoped commands that otherwise show up doubled.
- **`global.clients.musicEmbedManager`** (set at index.js:283-284): MusicPlayer and MusicEmbedManager are never wired via constructors — MusicPlayer reaches the embed manager through this global (13 reads in MusicPlayer.js, e.g. 1204, 1453, 1852). Keep it in sync with `client.musicEmbedManager`; don't pass the embed manager in when constructing a `MusicPlayer`.
- **HTTP server on `PORT`** (index.js:26-55): Default 8080. Binds immediately so Railway/Fly.io don't kill the container during the 5s startup delay. `/spotify-callback?code=` handles Spotify OAuth; every other path → `200 OK` (health check).
- **`STATE_DIR` env var** (Railway volume): When set, `audio_cache/`, `database/playerState.json`, and `database/spotify_token.json` all live under it. **Gotcha:** `LanguageManager`'s `database/languages.json` (node-json-db) ignores `STATE_DIR` — it's always cwd-relative, and every shard shares it.
- **`ytdlp-exec.js` wrapper** (`src/ytdlp-exec.js`): Converts camelCase option keys to `--kebab-case`; resolves binary from `node_modules/youtube-dl-exec/bin/` (falls back to `bin/`). Used by YouTube, SoundCloud, and MusicPlayer's download path (MusicPlayer.js:624). NOT used by DirectLink (which uses `axios`). `ytdl-core` is an **unused** dependency — no source requires it.
- **YouTube auth strategy** (`src/YouTube.js` `getYtDlpOptions`), fallback order:
  1. `cookiesFromBrowser` → `extractorArgs=youtube:player_client=mweb`
  2. `cookiesFile` env → `player_client=mweb`
  3. `COOKIES_CONTENT` env → materialized to a `fs.mkdtempSync` temp file (yt-dlp has no `--cookies-stdin`) → `player_client=mweb`
  4. `poToken` env (`YOUTUBE_PO_TOKEN` or `PO_TOKEN`) → `player_client=web` + `po_token` (format `web+TOKEN`)
  5. none of the above → `player_client=ios` (no auth)
  `jsRuntimes` is `node:${process.execPath}` (not just `'node'`). `getStream()` additionally tries formats (`ba/b`, `bestaudio`, `worstaudio`, `worst[acodec!=none]`) × clients (default, `android`, `tv,mweb`) until bytes flow — so format/client failures below the top tier are expected log noise. **Never use plain `worst`** as a fallback: it can resolve to a video-only format (`acodec=none`) → data flows but playback is silent. `downloadToFile()` (`src/YouTube.js`) uses the **same client × format fallback chain** for the background cache downloader — so a download that times out on the default (cookies→mweb) client can still succeed via `android`/`tv,mweb`/`web+poToken`. `downloadTrack` (`src/MusicPlayer.js`) passes the already-resolved stream format as the preferred first candidate. The concurrent-download wait loop is 180s (not 60s) because the chain can take a while.
- **`COOKIES_CONTENT` env var** (index.js:58-73): Raw Netscape cookie string written to `config.ytdl.cookiesFile` (or `./cookies.txt`) at startup — the primary Railway mechanism since its filesystem isn't persistent. Render's `/etc/secrets/cookies.txt` is auto-copied to `cookiesFile` or `/tmp/cookies.txt`.
- **`isLowMemory` hardcoded false** (`src/MusicPlayer.js:40`): Background track downloads always run so the play() fallback can switch from failed streaming to a cached file.
- **Session recovery**: `PlayerStateManager` persists active players to `database/playerState.json` on graceful shutdown and restores them on restart (reconnects voice, resumes playback). In shard mode, restore is broadcast after a 10s post-spawn delay (`shard.js:95`). Audio cache cleanup runs after restore (`restoreSessions`, index.js:378-383).
- **SIGINT vs SIGTERM gotcha**: There are two SIGINT handlers — a simple disconnect registered first (index.js:505, inside the startup timeout, before `init()` runs) that calls `process.exit(0)` immediately, and the state-saving graceful shutdown in `init()` (index.js:613) registered later. So on SIGINT the simple handler fires first and the graceful save is likely skipped; SIGTERM (what Docker/Railway sends) reliably saves state.
- **Spotify OAuth** (`src/Spotify.js`): Redirect URI `http://127.0.0.1:3000/spotify-callback` (NOT `localhost` — Spotify rejects it for new apps), override via `SPOTIFY_REDIRECT_URI`. Refresh token saved to `database/spotify_token.json`; read back from `SPOTIFY_REFRESH_TOKEN` env first (Railway persistence). Falls back to client credentials grant when no refresh token exists.
- **Spotify API change (2025)**: For apps created after April 2025, `GET /v1/playlists/{id}/tracks` returns 403. Code fetches `GET /v1/playlists/{id}` via `node-fetch` with `Authorization: Bearer`, parses top-level `meta.items`, uses `entry.item || entry.track`. Falls back to `spotify-web-api-node`, then web scrape (embed page / `__NEXT_DATA__`).
- **Sharding config** (`config.js` → `shard.js`): `TOTAL_SHARDS` (default `auto`), `SHARD_LIST`, `SHARD_MODE` (`process`/`worker`), `SHARD_RESPAWN`, `SHARD_SPAWN_DELAY` (5500ms), `SHARD_SPAWN_TIMEOUT` (30000ms).
- **No test/linter/formatter/TypeScript** — pure CommonJS. `npm test` = `node --check index.js` only. To validate changed files, run `node --check <file>` (e.g. `node --check src/YouTube.js`) — that's the de-facto verification practice.
- **Required Node.js**: `>=20.0.0` (package.json engines). Dockerfile uses `node:24-slim` + system python3 + ffmpeg, `NODE_OPTIONS=--max-old-space-size=384`, `EXPOSE 8080`.
- **ffmpeg bundled** via `ffmpeg-static` — no system install needed (Dockerfile installs ffmpeg anyway).
- **Postinstall hook** (`scripts/update-ytdlp.js`): Runs `yt-dlp -U` to update the binary; exit code 1 after an update is treated as success.
- **Gitignored**: `database/`, `audio_cache/`, `cookies.txt`, `.env`, `.claude/`, `discloud.config`.
- **Audio cache**: `track_[MD5].opus` files. Cleanup runs at startup (after session restore) **and every 15 min** (`CACHE_CLEANUP_INTERVAL_MIN`, index.js:182) — startup-only cleanup let the Railway volume fill up mid-session (`Errno 28`, only the first song loads). Deletes oldest-first once total exceeds **80MB** (`MAX_CACHE_MB` env, index.js:121). `getProtectedCacheFiles()` protects **only** `currentDownloadedFile` (the actively-playing file) per saved state — preloaded-but-idle files (e.g. whole-queue preload) are re-downloaded on demand and must NOT be protected, or the cache grows unbounded. **Two extra defenses in MusicPlayer:** (1) `trimCache()` runs immediately after every successful `downloadTrack` and trims back to `MAX_CACHE_MB` in real time (the 15-min sweep alone still let a big playlist add fill the volume first); (2) a **process-wide download concurrency cap of 3** (`MAX_CONCURRENT_DOWNLOADS`, module scope) — `addTracks` fires `preloadTrack` for the *entire* queue at once and each preload writes a full `.opus`, so without the cap N simultaneous yt-dlp writes flood the volume. The file is added to `downloadingFiles` *before* waiting for a slot, so `play()`'s error-path wait (`preloadInFlight`) can still detect a queued-but-not-started download.
- **22 language packs** in `languages/`. `LanguageManager` hot-loads every JSON file; guild prefs live in `database/languages.json` via node-json-db.
- **Transition message auto-delete** (`src/autoDelete.js` → `scheduleAutoDelete(target, ms=60000)`): every ephemeral transition message deletes itself after **60s** — pause/resume, skip, previous, stop, shuffle, loop, autoplay on/off, volume-modal success, `/queue`, `/nowplaying` (now ephemeral), and the resume-on-restore message (`MusicPlayer.js:2496`). The Queue button (`buttonHandler.js` `handleQueue`) is **ephemeral** + auto-deleted, and `handleQueuePagination` re-schedules the delete timer on each page change. **Exempt (never auto-deleted):** the main `/play` embed (`nowPlayingMessage`) and interactive embeds (search, language, lyrics). Standard pattern: `reply(...)` → `interaction.fetchReply()` → `scheduleAutoDelete(msg)`. Timers are `.unref()`'d so they never hold the process open.
- **Playback position reliability** (fixes autoplay double-play): `getCurrentTime()` (MusicPlayer.js:1742) only trusts `audioPlayer.state.resource.playbackDuration` when status is `Playing` **and** `playbackDuration > 0`; otherwise it falls back to wall-clock (`startTime`/`pausedTime`). `handleTrackEnd`'s `endedUnexpectedly` (MusicPlayer.js:~1773) uses `getCurrentTime()` directly — so a **genuine mid-track interruption** (wall position still well under duration) retries the same track up to 2× from the last position, while a **naturally-finished** track (wall position ≈ duration, e.g. from a cached `.opus` file where `playbackDuration` sticks at 0) is NOT wrongly re-played from position 0. Note: the position must be computed from `getCurrentTime()` — reading `resource.playbackDuration` raw will be 0 for cached-file playback and either falsely replay (if used without the Playing guard) or kill retries entirely (if the guard is too strict).
- **Silent-stream recovery** (MusicPlayer.js:~961): the 5s "no data received from stream" diagnostic is **not just a warning anymore** — if zero bytes arrive from the provider stream, it calls `audioPlayer.stop()` (with `pendingEndReason='watchdog'`) so the existing `endedUnexpectedly` retry path re-resolves a **fresh** stream and/or picks up the background-downloaded cache file. This fixes tracks stuck at 0:00 forever when the stream was resolved during **preload** (silent `getStream`) long before playback actually started — the yt-dlp pipe had gone stale. Guard: track-URL match, `!isTransitioning`, `!playingFromFile` (a mid-play `switchToDownloadedFile` swap stops the old provider stream's flow, so status=Playing alone would falsely kill the new .opus resource), and Playing/Buffering status. When the guard blocks recovery, it logs `Silent stream NOT restarted — guard blocked: status=...` so the next occurrence is diagnosable. Retries are bounded (2× per track via `currentTrackRetries`), then it falls through to skip. **Complementary mid-play stall watchdog** in `ensureTrackCompletion` (MusicPlayer.js:1330-1360): the 5s check only catches *never-start* streams — a pipe that dies **mid-play** leaves the player stuck in Playing/Buffering forever with `playbackDuration` frozen (the normal Playing branch keeps rescheduling by remaining ms and never fires Idle, so the queue freezes). A pure **wall-clock** position (`currentTrackStartOffsetMs + Date.now()-startTime + pausedTime`) is compared against duration: if it exceeds `duration + 10s` while Playing/Buffering, it force-stops (`pendingEndReason='watchdog'`) so `handleTrackEnd` advances the queue. Wall-clock is used deliberately — `getCurrentTime()` freezes during Playing (it prefers `resource.playbackDuration`), which would defeat the detector. Safe for cached-file playback: a finished `.opus` reaches Idle naturally (~duration wall-clock) before the 10s margin ever trips.
- **Decoded-PCM watchdog** (MusicPlayer.js `_startDecodedAudioWatchdog`): the 5s silent-stream check counts bytes from the **provider source** (yt-dlp stdout) — a format that delivers bytes but fails to DECODE (combined/DASH container, fragmented MP4, corrupt cached `.opus`) emits no PCM at all, so the log shows `✅ Stream producing data: 1290.8KB` yet playback is silent with no error. The watchdog counts DECODED PCM on ffmpeg's stdout across all three resource paths (stream/file/cache-swap) and force-stops (`pendingEndReason='watchdog'`) a Playing track that gets zero decoded bytes within 6s, so the `endedUnexpectedly` retry re-resolves fresh and/or picks up the downloaded cache file. Token guard (`_decodedWatchResource`) prevents a stale timer from killing a newer resource after `switchToDownloadedFile`. Related: the **stream-path FFmpeg args** now use `-analyzeduration 0` (was `1M` — probing 1MB on a ~2Mbps combined DASH pipe delayed/failed decode; file/swap paths already used `0`), matching the documented-working config at MusicPlayer.js:1172.
- **Gone-message 404 handling** (`MusicEmbedManager._isMessageGoneError`): editing `nowPlayingMessage` after the channel/message was deleted (channel deleted, bot removed) throws `DiscordAPIError[10003]/[10008]`; both `updateNowPlayingEmbed` and `handlePlaybackEnd` catch sites now swallow those (and HTTP 404) silently instead of dumping a full-stack `console.error` — which previously repeated every 10s via the progress interval.
- **Mid-play switch to cache** (`switchToDownloadedFile`, MusicPlayer.js:1266): the background downloader usually finishes within ~10s of a track starting. As soon as `downloadTrack` resolves, `play()` swaps the live resource from the fragile provider stream to the freshly-downloaded `.opus` **file, continuing from the current position** (`-ss`). This shrinks the stall-prone window (a yt-dlp pipe dying mid-play) to just the first ~10 seconds; the rest plays from stable local disk. Safe: discord.js's `play()` resource swap destroys the old stream and goes Buffering→Playing **without emitting Idle** (same path `seek` uses), so `handleTrackEnd` never fires spuriously. Position math is re-pointed (`currentTrackStartOffsetMs`, `startTime`) so the wall-clock watchdog/`getCurrentTime()` stay consistent. Refused (non-fatal) when paused/transitioning/skipping, near track end, already playing from a file (`playingFromFile`), or if the file doesn't exist yet.
- **Stuck-queue deadlock fix** (MusicPlayer.js play() catch ~1258): when `play()` fails to resolve a stream, it previously called `handleError()` **while `_playLock` was still held** (released only in `finally`) — `handleError`'s `play(null, 0)` returned `{success:false,'Already playing'}` and was ignored, freezing the queue (previous track ended, next never started). This is the classic symptom of "queue stops after a track whose `getStream` hit a transient **No playable format found** while the background `downloadTrack` later succeeded". Three-part fix: (1) release `_playLock` **before** `handleError`; (2) if the failed track has an in-flight download (`downloadingFiles`), wait up to 60s for the file and **retry `play()` from the cache** — so the track plays instead of being skipped; (3) `handleError` now returns the result of the advanced `play()` and `play()` propagates it (`{success:true,track}`) so callers (e.g. `handleTrackEnd`'s `if (!result.success)`) don't clobber the now-playing `currentTrack`. Verified by a stub-based harness: all-fail drains the queue, fail-then-succeed advances without clobbering, in-flight-download retry plays from file. Related: `play()` now checks the downloaded cache file **before** resolving a provider stream (MusicPlayer.js:776) — avoids a wasted yt-dlp spawn per track whose `.opus` already exists.
- **Phantom pause fix** ("next song has no audio" + frozen 0:00 bar): `pauseFor()` (MusicPlayer.js:1660) used to add the reason to `pauseReasons` **before** checking player state — a pause click while the player was Buffering/transitioning added a phantom `'manual'` entry even though `audioPlayer.pause()` failed. That stale reason then made `play()` auto-pause **every subsequent track** (silent — the log signature is `⏸️ Paused due to: manual` right after `▶️ Playing: ...`) and froze the progress bar (`startProgressUpdate` skips when `player.paused`). Three-part fix: (1) `pauseFor` only records the reason on a *successful* pause; (2) `play()` resets `this.paused = false` when starting a track; (3) `handleTrackEnd` deletes `'manual'` and `'alone'` on track end/advance/retry so they never carry over — **`'mute'` is deliberately kept** (explicit mute must persist across tracks). The `'mute'` reason (index.js:474) and `'alone'` (inactivity) are unaffected.
- **Stale preloaded-stream fix** ("next song has no audio" despite `▶️ Playing` + no getStream logs before it): `addTracks` fires `preloadTrack` for the **entire queue**, and `preloadTrack` resolves a real yt-dlp pipe (`YouTube.getStream`) per track and stores it in `preloadedStreams`. By the time a deep-queue track actually plays, that pipe has sat unread for **minutes** and delivers 0 bytes → silent track stuck at 0:00. Two-part fix in MusicPlayer.js: (1) `play()` now **discards preloaded streams older than 60s** (`preloaded.at` timestamp; the 60s window only preserves the genuinely-next track's instant-start) and re-resolves a **fresh** stream — the log signature for a discarded stale preload is `Discarded stale preloaded stream for "..." (Ns old) — resolving fresh`; (2) a **concurrency cap of 3** (`MAX_CONCURRENT_PRELOADS`, module scope, mirrors the download cap) stops addTracks from spawning N simultaneous yt-dlp getStream processes that rate-limit YouTube (the recurring `No playable format found` on preloads that downloadToFile succeeds on) and hold N idle stale pipes. `downloadTrack` is independent of the preload's getStream result (it derives its own URL and calls `YouTube.downloadToFile` with its own fallback chain) — `streamInfo.format` is only a `preferredFormat` hint — so discarding stale preloads costs nothing downstream.
- **Autoplay**: Toggle via the 🎲 button or `/autoplay` (both just set `player.autoplay = 'related'` — no genre picker). When the queue ends, `MusicPlayer.handleAutoplay` first grabs YouTube related videos from the **last played track**; on failure it falls back to a **region-aware search** built by `buildAutoplayKeywords` from `detectRegionHint()` (scans `previousTracks`+queue titles/artists: non-Latin script → Hindi/Arabic/Korean/Japanese/Russian/Thai/Chinese; Latin → Indonesian via word dictionary; else generic `music official video` / `top songs ${year}`). Results are bias-filtered by `filterByRegion` for non-Latin scripts. Filters 30s–600s and blocks tutorial/podcast/etc. titles. It plays 1 candidate immediately, then tops the queue up to ~50 tracks in the background via `refillAutoplayQueue` (3 parallel searches, deduped by URL against the queue + `previousTracks`). While the last queue track plays, `prepareAutoplayCandidate` preloads a related candidate into `pendingAutoplayTrack` so the next autoplay transition is ~instant; downloads stay **per-track** (only the next one is preloaded — 50-track refill is metadata only). If it finds nothing, it clears `currentTrack` and falls through to the normal queue-completed cleanup instead of leaving the player stuck. `previousTracks` is capped at 50 entries. (The old genre-select menu is gone — `player.autoplay` is binary off/`'related'`; a stale comment at MusicPlayer.js:74 still references genre strings.)
